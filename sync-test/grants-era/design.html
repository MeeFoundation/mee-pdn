Sync reliability test: one phone against many nodes

Design draft, 2026-09-28 · Русская версия

Summary

One command, one phone, ten laptop nodes: the test sends 10,000 numbered entries to the phone over real Wi-Fi, cuts the phone's network for 30 seconds in the middle, and ends with PASS, FAIL or INCONCLUSIVE plus latency percentiles. The only manual step is having the phone on a cable, unlocked, on the same Wi-Fi.

The scenario in brief.

  1. Ten writer nodes on the laptop connect to the phone and grant it every path they will write.
  2. Each writes one numbered entry every 100 ms for 100 seconds.
  3. From 40 to 70 seconds a firewall rule cuts the phone off from the nodes; the test's own control channel stays up.
  4. Every node, the phone included, reports each entry it receives and each sync session it finishes.
  5. Writing stops; the test waits for one more successful session per writer, then lists what the phone holds.
  6. Every entry is classified, and the verdict and the numbers are printed.

The key rule, by example. The phone pulls from each writer in a sync session every 5 seconds, and a session carries everything the writer held when it started.

  • Entry 417 of w3 is written at 41.203. At 43.000 the phone lacks it, but no session with w3 has started since the write: in flight — normal.
  • A session started at 43.900 and ended ok on both sides, and 417 had not arrived by the phone's end of it: violated — a defect, however long we wait.
  • The partition never lifts, so no session ever qualifies: stalled — the run is INCONCLUSIVE, neither a pass nor a proven loss.

What a report looks like (the format, not a measurement):

VERDICT: FAIL — 1 violated, 1 lost
expected 10,160 · readable 10,159 · stalled pairs 0 · split sessions 0 · undetermined 0
latency, steady phase: p50 3.1 s · p90 5.6 s · p99 6.4 s (clock ±4 ms)
partition: first session 1.2 s after reconnect · catch-up 7.9 s
path: direct Wi-Fi, no relay · host CPU peak 58%
LOST w3 s/000000417 -> phone: w3 accepted 43.900-44.050 ok, phone ok at 44.185; logs tmp/run-20260928-1412/

The rest of this document gives the whole scenario, how every number is computed, and why each can be trusted — including the planted defects the test must catch before its numbers count.

What the test answers

The test answers two questions about sync between one physical phone and many nodes over a real Wi-Fi link: does every entry that should arrive actually arrive, and how long does it take. It separates an entry that has not arrived yet from one that sync has already failed to deliver, and it says so without a waiting timer.

It answers, per run:

  • how many entries were delivered, lost, corrupted, stale, or present where no grant allows them;
  • how long an entry takes from its write to being readable on the reader, as percentiles;
  • how long the phone takes to catch up after its network is cut and restored;
  • whether the run itself can be trusted: host CPU, event loss, clock error, network path.

It deliberately does not answer:

  • relay and NAT traversal performance. The main run uses a direct Wi-Fi path; a relay run is a separate variant, because a public relay's load would sit inside the number.
  • battery and radio cost. The phone stays in the foreground on the agent screen; iOS stops the node in the background, which is a separate scenario.
  • what a withdraw does to data already delivered. The grantee unbinds and forgets the issuer's replica once the withdraw replicates; the withdraw scenario checks that nothing written after the withdraw arrives, and that the phone then refuses that issuer.
  • throughput limits of one laptop. When the host CPU saturates, latency is reported as the machine's limit, not the platform's.

Setup

One laptop runs every node and the coordinator; one physical iPhone runs a test build of the application; both sit on one Wi-Fi network. The manual preparation is the phone alone: connected by cable, unlocked, auto-lock off, on the same Wi-Fi as the laptop, and the test build installed once with Local Network access allowed — iOS asks for that permission on every fresh install, and only a person can answer it, so runs reset the node's storage instead of reinstalling.

Entries between the phone and every laptop node travel as iroh QUIC over direct UDP through the router. The shaper touches only that UDP; the coordinator reaches the agent over TCP, so cutting the phone's data path never cuts the test's control of it.

Participants.

ParticipantWhereRole in the main run
Writers w1..wNlaptop, one pdn-node-http process eachIssuers: each connects to the phone, grants it every slot up front, then writes

A slot is a path granted in advance for one entry the run will write. The two controls exist because a test that only proves authorized parties receive data verifies nothing about access (access-control-tests.md). outsider gets its ticket by a hand-made handover from the coordinator, not through the product: without a ticket it would never dial w1, and receiving nothing would prove nothing. A hand-made ticket is admitted for exactly this kind of negative control (product-path-arrangement.md). One denial is out of reach today: a party that knows a payload's hash can fetch that blob, because the blob channel is not yet gated (a deferred gap in the subset-reconciliation spec). The report lists it as a known gap, not a pass.

Why this network arrangement.

  • The phone's radio carries every one of the N connections, so the mobile node is under real load: CPU, radio wake-ups, iOS socket behaviour.
  • The phone can be cut from a script. Laptop nodes run PDN_CONNECTIVITY=direct and so have no relay; the only path from the phone to them is direct UDP. pf rules dropping UDP to and from the phone's IP are a real partition of the real phone, and the control channel, which is TCP, passes.
  • Delay and loss use the same rules. dummynet, macOS's own traffic shaper, holds or drops packets in the kernel, so the QUIC under iroh meets real delay, loss and retransmits. The test adds rules in both directions for the phone's address, on the interface route get <phone IP> names, and proves them by pf's own rule counters after a UDP probe.
  • Loopback between laptop nodes is not shaped, so what is measured is the phone's path, not the laptop's.

Two things on the laptop can defeat this silently. Docker Desktop puts containers behind NAT, so no node the phone talks to runs in one. The macOS application firewall can drop inbound UDP to a freshly built, unsigned pdn-node-http; the connect step fails loudly if the phone cannot reach a node, rather than measuring a relay or nothing.

The run, step by step

One command runs the whole scenario and ends with a verdict; nothing in it waits for a person.

sync-test --writers 10 --entries 1000 --rate 10 --payload 256 --scenario partition

The numbers below are the defaults of the main run: 10 writers, 1,000 entries each at 10 entries a second (100 seconds of writing), 256-byte payloads, a 30-second partition in the middle.

  1. Preflight. The coordinator checks the phone is attached (xcrun devicectl list devices) and records the git revision, the build profile and the host's core count.
  2. Bring up. Fresh directories for every laptop node; 10 writers and 2 controls start from a release build.
  3. Launch the agent. The coordinator launches the test build over the cable (xcrun devicectl device process launch), passing its own address and a run id as launch environment; a small native module hands them to JavaScript, which cannot read the process environment itself. The agent connects back over HTTP, deletes its node's storage directory inside the app container, brings up a fresh node and creates one identity — a clean state without a reinstall, which would ask for Local Network permission again. It reports the phone's Wi-Fi address.
  4. Network check. The coordinator finds the interface toward the phone (route get <phone IP>), installs pf rules for UDP to and from that address with no delay and no loss, sends a UDP probe, and aborts unless the rules' counters rose.
  5. Clock sample. The coordinator and the agent exchange 20 timestamped pings and keep the one with the smallest round trip; this repeats every 30 seconds for the whole run.
  6. Connect and grant. Each writer mints an invite; the agent consumes it, which fails loudly if the phone cannot reach that node. Each writer then publishes one grant to the phone covering its 1,000 s/ slots and its 16 h/ slots. partial connects to w1, which grants it the even slots; outsider receives w1's ticket by the handover. The coordinator waits until each grant is readable on its grantee, so grant traffic is over before measurement starts.
  7. Subscribe. The coordinator opens /debug/events on every laptop node, and the agent starts forwarding the phone node's events. From here on every entry arrival and every finished sync session is recorded, timestamped where it happens.
  8. Steady phase (0–40 s). Every writer writes its next entry every 100 ms, and every 5 seconds a new version of one h/ slot.
  9. Partition (40–70 s). The coordinator switches the pf rules to drop. Writers keep writing. No session between the phone and a writer succeeds; entries written now pile up as in flight.
  10. Recovery (70–100 s). The rules pass traffic again; writing continues to the end of the 1,000.
  11. Quiescence. Writing stops. The coordinator waits until, for every writer, a qualifying session that started after that writer's last write has been reported ok by both sides (defined in the classification section). A pair with no such session within 5 × the phone's reconcile interval (25 seconds) is stalled, and the run cannot pass.
  12. Final listing. The agent lists every writer's namespace on the phone and uploads the list; the controls are listed on the laptop. Both use an unnudged listing, so the listing itself starts no session. The agent's local journal is pulled over the cable (xcrun devicectl device copy from), so an event report that never reached the coordinator over HTTP is not mistaken for a missing entry.
  13. Verdict. Every expected entry is classified for every reader, the controls are checked against their expected sets, the metrics are computed, one row is appended to runs.csv, and the verdict is printed: PASS, FAIL or INCONCLUSIVE.

Test data and what is recorded

Every write is individually observable, every observation carries a timestamp taken where it happened, and nothing the test does to observe starts a sync.

Entries. Each writer writes s/000000001, s/000000002, … once each and never rewrites a slot, so each entry is its own unit of measurement; fixed-width numbers keep listings and logs in write order. A write replaces only the entry at its own key (put in crates/pdn-store/src/ranger.rs). A separate small set h/000001..h/000016 is rewritten with a rising version number. For these only the last version is expected anywhere: earlier versions can be superseded before any session sees them, and they are not classified.

Payload. Self-describing and self-checking, padded to --payload bytes:

{"run":"20260928-1412","writer":"w3","seq":417,"pad":"xxxx…","sha256":"9f2c…"}

sha256 covers the other fields. A reader can prove an entry intact without asking the writer, and a payload from another run, another writer or another slot is recognisable as such.

Grants up front. A claim covers exactly one path (covers_key and egress_filter in crates/data-layer/src/access.rs), so every slot the run will use is granted in step 6, before measurement. A grant republished during the run would put grant traffic inside the entry numbers.

Writer journal. For each entry, one line once the write call has answered:

FieldExampleSource
writer, seq, pathw3, 417, s/000000417the coordinator
t_write12:00:41.203the entry's own timestamp, set by the writer's node at insert (timestamp() in crates/pdn-store/src/sync.rs), on the writer's clock
sha2569f2c…the coordinator
resultok / refused + reasonthe write call

t_write travels inside the entry, so the phone sees the same value, and the coordinator's own HTTP round trip never enters it. A refused write is not expected anywhere and is counted on its own line of the report: it is a writer failure, not a sync loss.

Event log. Every node reports these events from the sync engine's own stream (LiveEvent in crates/pdn-store/src/engine.rs), timestamped in Rust where the event is produced:

EventRecorded fieldsUsed for
InsertRemotenode, namespace, path, entry timestamp, sending peer, content status, timeArrival of the entry
ContentReadynode, content hash, timeThe entry becomes readable: a fresh payload is a separate blob, downloaded after the entry
PendingContentReadynode, timeDownloads queued by the last sync have completed or failed
SyncFinishednode, peer node, origin (dialed or accepted), started, finished, ok or errorWhich sessions happened, when, and how they ended
Laggednode, timeThe engine's stream dropped events: the entries they reported are in the replica, the sessions and downloads they reported are gone

Laptop nodes expose the stream as a new debug route, /debug/events; the phone's node exposes it to the agent through the test build's facade. Each hop — the route, the facade to the agent, the agent to the coordinator — numbers its events, and a gap in the numbers is treated like Lagged.

No sync started by observing. Both a product read and a product list of a replica received under a grant nudge a sync (nudge_scoped in crates/data-layer/src/node.rs). A test that polled the phone would therefore be measuring its own polling. The run observes through events only. The final listing uses an unnudged list that does not exist yet: read_unnudged is test-only and reads one key, so the facade's test build and the debug route both need an unnudged list. The app's own screens do poll; a separate active reader variant polls like a screen does, and its rows are labelled as such.

Clock samples. Every 30 seconds, the coordinator and the agent exchange timestamped pings; the sample with the smallest round trip gives the offset of the phone's clock and its error bound, half that round trip. The offset is used for latency only — the classification never compares two devices' clocks.

Classifying every entry

An absent entry becomes a failure only when a sync session that must have carried it has ended successfully on both sides, and the entry is still not on the reader. Elapsed time alone never turns not yet into lost, and no decision compares two devices' clocks.

How entries actually move. Gossip carries no entries: a local write only announces "this author has news", and entries travel only inside a reconciliation session (on_replica_event in crates/pdn-store/src/engine/live.rs; the swarm is content-free). A replica received under a grant does not join the swarm: its holder's reconcile pass — a loop that re-dials every tracked replica's contacts every interval, 5 seconds on the phone — opens a session with each writer (reconcile_pass and SyncStrategy::ContactsOnly in crates/data-layer/src/node.rs). Waiting up to one interval is therefore normal.

Writers dial the phone too: after one successful session a writer records the phone as a peer, and its own pass dials it (register_useful_peer in live.rs). Those sessions address the writer's own identity rather than the phone's, and are expected to fail or carry nothing. The rule never uses them; they are reported separately under session health.

The guarantee the rule stands on. A session serves a view of the writer's replica frozen when the session is set up (sync_session_start in crates/pdn-store/src/actor.rs), and a successful session leaves the reader holding everything in that view its grant covers. The first half is specified; the second has no test that isolates one session, which is why such a test is step 0 of the build order.

Why both sides must report ok. The writer's report alone is not enough. When the dialing side fails midway, it still closes its stream cleanly (connect_and_sync_inner in crates/pdn-store/src/net.rs), and the accepting side reads that end as a normal finish (run_rounds in crates/pdn-store/src/net/codec.rs). The writer then reports ok while the phone reports an error. A session that is ok on one side only is not used by the rule; it is a finding of its own, a split session.

The qualifying session for entry e of writer W and reader R is one session dialed by R and accepted by W in which:

  1. W's SyncFinished (origin accepted, peer R) is ok, and its started is later than e's t_write — both on W's clock. started is taken before the view is frozen, so the view holds e.
  2. R's SyncFinished for the same session (origin dialed, peer W) is ok. The pass never starts a second session for a pair while one is running, so the two sides' events pair up one to one, in order.

e must then be on R by the time R's side finished: an InsertRemote for e on R no later than that finished, both on R's clock.

Worked example, entry s/000000417 of w3, read by the phone:

  • 41.203 on the laptop's clock — w3 writes it; that is the entry's own timestamp.
  • 43.000 — the phone does not have it, and no session with w3 has started since the write. In flight. That the phone already has 418 or 416 says nothing: reconciliation does not deliver in write order.
  • The phone's pass dials w3. w3 reports the session accepted, started 43.900, finished 44.050, ok (laptop clock) — it started after the write, so its view holds 417. The phone reports the same session ok, finished 44.185 on the phone's clock. The session qualifies.
  • The phone's InsertRemote for 417 is at 44.160 on its clock, before 44.185: delivered in that session. Its payload blob follows with ContentReady at 44.240. The phone's clock runs 0.130 s ahead (±0.004 s), so it became readable at 44.110 on the laptop's clock: latency 2.907 s ±0.004 s.
  • Had there been no InsertRemote for 417 by 44.185 on the phone's clock: violated. If it arrives in a later session, it is also counted late after violation; if never, lost. Either way it is a defect, and the report names the session that should have carried it.
  • Had w3 reported ok and the phone an error for that session: not a violation but a split session, and 417 stays in flight for the next one.

A session that started before the write (the grey bar) proves nothing, however late it finished: the writer may not have held the entry when its view was frozen.

SyncFinished names the peer's node, not its identity. The main run hosts one identity per node, so the node identifies the counterpart; variants with co-located or linked identities need the identity added to the event first.

Metrics and how each is computed

Every number in the report is computed from three inputs only: the writer journals, the event logs, and the final listings. Latency is a measurement; it becomes a pass condition only once a threshold is agreed per scenario.

Verdict.

  • FAIL — any defect: violated, lost, content lost, split session, corrupt, extra, stale.
  • INCONCLUSIVE — no defect, but at least one stalled pair, or undetermined pairs above 1% of expected: the run could not show whether something was lost.
  • PASS — neither of the above.

Counts. An expected pair is an entry and a reader it must reach: every s/ entry whose write returned ok, and the last version of every h/ slot, times every reader whose grant covers it.

Latency — per readable pair, in seconds:

latency = t_readable(R) − offset(R) − t_write(W)

t_write is the entry's own timestamp. t_readable is the ContentReady time of the payload's hash on the reader's clock — or the InsertRemote time in the rare case the content was already complete. offset is the reader's clock minus the laptop's from the nearest clock sample, 0 for a laptop reader, and each value carries that sample's error bound.

  • Reported as p50, p90, p99 and max with nearest-rank percentiles, separately for each phase (steady, partition, recovery) and for each reader: mixing phases would let 30 seconds of partition dominate the tail and hide the steady-state number.
  • Pairs readable only through the final listing (their events were lost) have no latency and are counted, not guessed.
  • The steady-phase shape is roughly known in advance: the wait for the reader's next pass (the interval plus the pass's own time, longer when a pair's previous session is still running and the pass skips it), then the session, then the blob download. A p50 of several seconds with a 5-second interval is the design, not slowness. The open reconcile-trigger change in mia-docs would replace this shape entirely.
  • Clock checks. A corrected arrival must lie between the entry's t_write and the finished of the writer's side of the session that carried it, both on the laptop's clock, each widened by the error bound. An arrival outside that window in either direction means the offset is wrong, and the run's phone latencies are marked invalid. The classification is unaffected: it never uses the offset.

Recovery — for the partition scenario:

  • time to first session = the first qualifying session between the phone and any writer after the pf rules pass traffic again, minus that moment;
  • catch-up time = the last t_readable among entries written during the partition, minus that moment;
  • time to converge = the last t_readable of the run, minus the last t_write.

A session running when the cut starts can hold its pair until the transport gives up — the QUIC idle timeout, or SYNC_SESSION_TIMEOUT of 300 seconds in crates/pdn-store/src/net.rs — and the pass skips that pair meanwhile. Such sessions are listed beside the recovery times, because they, not the network, can set them.

Session health — per writer–reader pair and per origin (dialed by the phone, dialed by the writer): successful, failed and split sessions, their error strings, and the gaps between successful sessions. A median gap far above the reconcile interval means the pass is not running as configured, which explains latency before anyone blames the network.

Why the numbers can be trusted

The test is trusted for two reasons: each known way a sync test lies is closed by construction, and the test is itself run against planted defects and must report each one as exactly what it is.

The test is tested. Before its numbers count, the harness runs against defects planted on purpose, with a laptop node standing in for the phone. Each must come out as exactly the stated report; a harness that reports any of them as PASS is broken.

The suite needs two things the laptop does not have today: a reconcile-interval setting for pdn-node-http, which uses the runtime's 10-second default, and, on a Linux pipeline where pf does not exist, another way to cut a node — stopping the reader's process, or nftables inside a container. This mirrors the repository rule that a test rewritten onto the product path must fail with its mechanism deliberately broken (product-path-arrangement.md).

What a clean run proves, statistically. Zero losses in n independent trials bounds the loss rate below 3/n at 95% confidence (the rule of three, flaky-tests.md). Entries are not independent: a failing session tends to lose many at once. So the report states two bounds. Per session, the honest one: the main run has about 130 qualifying sessions (10 writers, one every 5 seconds or so over the 70 seconds the network is up), so a clean run bounds the rate of losing sessions below 3 in 130. Per entry, 10,160 pairs, valid only if losses were independent. More confidence comes from more runs, not a longer report.

Every defect found is reproducible. The report names the writer, the reader, the seq, t_write, both sides of the session that should have carried it, and the log directory. That is enough to replay the case as a scenario test in the workspace, where it is fixed and pinned, as flaky-tests.md asks.

Facts to confirm, and the build order

The design rests on properties of the code and the tools that were read but not yet exercised; each is confirmed first, and a failed one changes the design before anything is built on it.

To confirm or build in the code:

  • One successful scoped session leaves the grantee holding every covered entry of the view it served — the claim the classification rests on. No test isolates it today: crates/data-layer/tests/read_restriction.rs polls read, which nudges, so it proves eventual convergence, not one session.
  • The replica applies an insert, timestamp included, before it opens any session's view: the timestamp is taken inside the insert (Record::new_current in crates/pdn-store/src/sync.rs), and started precedes the view. If a session could freeze its view between an entry's timestamp and its insert, a session started after t_write could miss it without any defect.
  • The dialing side sends Abort when its exchange fails, instead of closing cleanly. Without it the writer reports ok for a session the reader failed; a host can trigger that through the public surface, so it is a fix, not a note.
  • What writer-dialed sessions to a grantee actually do: fail, or succeed carrying nothing. The rule excludes them either way; session health needs to know which.
  • A node on Connectivity::Direct puts its LAN address in an invite, and a phone node on for_product dials it directly. Nothing has exercised this path yet.
  • Event subscription for a data namespace from pdn-node, a /debug/events route, and the same stream in the facade: none exists today.
  • An unnudged list, in the facade's test build and in the debug routes.
  • A reconcile-interval setting for pdn-node-http.
  • A grant of 1,016 claims fits the entry payload limit and publishes in reasonable time.
  • iroh tells, per remote node, whether the connection is direct or relayed, for /debug/paths.

To confirm in the tools:

  • xcrun devicectl device process launch passes environment variables, a native module exposes them to JavaScript, and xcrun devicectl device copy from reads the app's data container.
  • Local Network access survives relaunching the app and deleting the node's directory; only a reinstall asks again.
  • pf rules for the phone's IP on the interface route get names drop its UDP in both directions while TCP passes, and their counters show it.
  • The macOS application firewall lets inbound UDP reach a freshly built pdn-node-http, or is told to.

Build order. Each step is usable on its own, and the phone arrives last, onto a method already proven on the laptop.

  1. The single-session test, in the workspace: covered and uncovered entries, exactly one scoped session, the grantee holds every covered entry and no uncovered one. Nothing below is built before it passes.
  2. Network spike, about half a day: the direct path, the pf rules and the firewall, by hand.
  3. pdn-node-http: /debug/events with numbered events, /debug/paths, the unnudged list, the reconcile-interval setting.
  4. Coordinator and the planted-defect suite, laptop only. Every row of the planted-defect table passes before step 4.
  5. OpenSpec change in mobile-common: the test build, the agent, its control channel, the event stream and the unnudged list in the facade. The application's README states that it speaks no HTTP to anything, and its behaviour is specified in mobile-common, so this is specified before it is built.
  6. The agent in pdn-app, then the steady and partition scenarios on the phone.
  7. The remaining scenarios, then the network variants: a router with its own shaper, LTE with relays, a second phone.

The coordinator is a Python script using only the standard library, run as python3 -I, as the repository's rules for scripts require. It lives in pdn-app/sync-test/, because it stages this application.
