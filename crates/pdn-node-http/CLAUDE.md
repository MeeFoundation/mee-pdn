# crates/pdn-node-http

The thin HTTP host for the demo stand: an axum binary embedding one runtime. `GET /live` always on; the `/debug/` subtree is scaffolding behind `PDN_DEBUG` set to `1` or `true` (absent when unset, `0` or `false`; any other value stops the start; route names unpinned) and covers the runtime's five services — identities, the pairing and linking ceremonies, connections and grants, entries, pods — one route to one service call, with entry, record and operation payloads as raw bodies and everything else as JSON. Every data route names the identity performing the operation before the issuer (`/debug/data/{identity}/{issuer}/{*path}`), and every pods route the identity before the pod (`/debug/identities/{identity}/pods/{pod}/…`), because an operation acts for the identity it names and for that one alone (ADR-0013). Refusals arrive as refusals: one closed error table maps the runtime's typed errors to statuses (403 refused, 409 not hosted or no member, 400 malformed, 404 absent, 500 unrecognized).

Deliberately absent, and to stay absent: any namespace or pod store ticket handover (a grant read hands back the capability alone, a pod invite a one-time secret), any raw entry written into a pod's store (forgeries are the data layer's tests), anything that forces reconciliation or resets state, and any handler addressing another host — the crate carries no HTTP client, and inter-node traffic is the runtime's own protocols.

Env: `PDN_DATA_DIR` (required — the runtime's storage directory; the host offers no in-memory mode, so unset stops the start naming the variable, and a directory the runtime cannot use — unwritable, held by another running node — stops it the same way, serving neither liveness nor the debug surface), `PDN_HOST` / `PDN_PORT` (default `127.0.0.1:3011`, loopback so a wider bind is deliberate). Depends on `pdn-node` only — no direct `data-layer` dependency.

Its tests drive the surface across containers and nowhere else (`tests/stand*.rs` over the harness in `tests/common/`): the runtime's own behaviour is proven by `pdn-node`'s scenarios, so a second in-process run of the same flow through HTTP would be a third copy of it. The stand (`ops/Dockerfile`, `just test-docker`, and its own CI job) runs each node as its own process in its own container on one network per test, with HTTP published to the test host and nothing but the runtime's own protocols between nodes. Two tests that build a runtime stay in this process, each for a property of the host that no request on the surface can produce, since none can stall the runtime's coarse state lock: `tests/readiness.rs` holds that lock from inside to show `/live` answering while `/ready` reports the wait, and `tests/admission.rs` holds it to keep the `/debug/` ceiling's worth of requests in flight and show the one past it shed. The unit tests in `src/` run in the test process too: each tests one of the host's own functions alone — the error table, the parsers, the environment, the admission function, the runtime budget — and starts no runtime.
