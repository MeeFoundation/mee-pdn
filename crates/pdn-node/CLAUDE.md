# crates/pdn-node

The embeddable runtime core: identity / connections / data / sync services as thin glue over `data-layer`, plus the runtime's two ceremonies.

Pairing (ADR-0011): connections are produced by establishment — `invite` mints a bearer-free payload carrying a one-time secret (no ticket, no identity proof — nothing grants durable access; the secret burns on first use), `establish` dials the pairing ALPN and runs the verify-and-burn dialogue, and the grant surface publishes, withdraws and reads grants over the connection's metadata pair — the peer's half for what the peer granted, capability and ticket together, the identity's own half for what it granted itself, capability alone (no manual recording).

Device linking (ADR-0012, the `linking` module next to `pairing`): `linking_invite` mints the same kind of bearer-free payload (one-time secret inside, nothing durable), `link` dials the linking ALPN — the inviter verifies-and-burns, registers the newcomer's device record itself (from the connection's authenticated peer id), and replies with fresh directory and data-namespace write tickets; `link` imports both and returns caught up, rolling both back on failure.

Each `Runtime` is one running node hosting any number of identities, each added by an explicit act (create, or link from a payload); the runtime is the single owner of node assembly — both protocol handlers thread through `spawn` into data-layer's protocol slot — and of the hosted identities' store handles. Every operation of every service names the identity performing it and acts for that identity alone (ADR-0013): an issuer only a co-located identity holds is unknown to the caller, exactly as an issuer no identity here holds is, and an operation naming an identity this node does not host is refused as `UnknownIdentity`. Services are traits with one production implementation each; `IdentityService` mints placeholder `PdnId`s with no key material behind them. Cross-identity access is the grant surface: a grant published over a connection's metadata pair binds the granted namespace on the audience by itself (the grant binder in `connections.rs`), and the data service's ticket share/import remains for a ticket obtained out of band — a bare ticket delivers nothing from an armed issuer, and what one identity imports is re-served to nobody. Two identities of one node meet inside the process: iroh refuses a connection to its own endpoint id, so both ceremonies' dialogues and every sync session between them run over a pipe, under the same messages and the same classification as between two nodes.

Hosting survives a restart on a directory-configured runtime (`SpawnOptions::on_directory`): each hosted identity's own subdirectory carries its hosting record — the namespace of its directory, written at the commit point of the create or link, after provisioning and before hosting — and `spawn` re-hosts every identity whose subdirectory holds one, through the same tail `create` runs, with the data namespace, the metadata pairs and the granted namespaces re-derived from the directory by the connection armer's sweeps. An unreadable record stops the start; a subdirectory without one is an unfinished create or link and hosts nothing; on a memory runtime hosting ends with the process.

Scenario tests in `tests/`. No host or HTTP dependencies.
