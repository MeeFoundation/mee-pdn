# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

`pdn-store` implements multi-dimensional key-value *documents* (called **Replicas**) that synchronize between peers using **range-based set reconciliation** (Aljoscha Meyer's algorithm, [paper](https://arxiv.org/abs/2212.13567)).

It is the platform's own variant of n0's `iroh-docs` (ADR-0016): it holds what a crate of the workspace reaches, carries the workspace's version and is never published. The wire protocol keeps upstream's ALPN, `/iroh-sync/1`.

[`UPSTREAM.md`](UPSTREAM.md) carries the crate's two duties toward upstream: at every bump of iroh, iroh-blobs or iroh-gossip, a pass over upstream's new commits and open fix pull requests, each with a verdict; and a look at upstream before a change that needs the store to do something new.

Two non-obvious facts shape the whole design:

- **Documents store hashes, not content.** Each *Entry* maps a key to the BLAKE3 hash, size, and timestamp of some content — the content bytes themselves are never stored in or transferred through a replica. Actual blob transfer is delegated to `iroh-blobs`.
- **`Docs` is a "meta-protocol."** It composes `iroh-blobs` (content) and `iroh-gossip` (live notification) on top of an `iroh` endpoint. Setting up `Docs` requires wiring up an iroh-blobs store and `Gossip` too, and mounting `DocsDispatch`, the one accept path (`tests/util/mod.rs` shows the assembly).

Entries are signed by two keypairs: a **Namespace** key (write capability; its public `NamespaceId` is the replica's unique id) and an **Author** key (proof of authorship; any number of `AuthorId`s, with app-specific meaning).

## Common commands

One crate of the `mee-pdn` workspace, at `crates/pdn-store`; every command runs from the workspace root through `just`. The package and the directory both read `pdn-store`, with no workspace alias between them — `-p pdn-store` selects it, and code names the crate `pdn_store`.

- **Format**: `cargo fmt --all` under the workspace `rustfmt.toml`; `just check` verifies it. Imports stay grouped std / external / crate with one `use` per crate — stable rustfmt preserves that grouping rather than imposing it, so a new import is placed in its group by hand.
- **Test** (nextest): `just test -p pdn-store`; `-E 'test(test_name)'` selects one test. Two configurations: no feature, the one the product ships, which `just test-product` runs the suite in, and `observation`, which `just test -p pdn-store` turns on.
- **Lint**: `just check` lints the store, every target, with warnings denied under the store's own `[lints]` table, and builds its docs with rustdoc's warnings denied (an intra-doc link to a private item is one).

## Pre-push checklist

Run from the workspace root before a change here is committed; every item is a blocking check:

1. `just check` — fmt, clippy and type-check of the whole workspace with the store's warnings denied, and every crate's docs, private items included, with rustdoc's warnings denied.
2. `just test` — the workspace's tests, the store's among them.
3. After a change to sync, the engine, or the wire format: the flaky-test stress pass the workspace `CLAUDE.md` asks for, over the scenarios in `crates/data-layer/tests` and `crates/pdn-node/tests` that reach the changed code.

## Public surface

An item is public only when something outside the store's sources names it — another crate of the workspace, or one of the store's integration tests — or when a public item's signature carries it, which the compiler requires: `QueryBuilder` stays public behind `Query::all`. Every other item is crate-private, so one nothing calls is a dead-code warning, which `just check` denies. An item named only by the integration tests stays public, and is the one place the rule holds by review: the compiler does not see those users.

## Architecture

Requests flow top-to-bottom; each layer is in its own module. The two key indirections are that **all store access is serialized through a dedicated actor thread**, and **live networking is coordinated by a separate async actor**.

```
Docs (protocol.rs)          ── entry point, holds the engine. Builder: Docs::memory()/persistent(path).spawn(endpoint, blobs, gossip)
  ├─ DocsDispatch           ── iroh ProtocolHandler: hands an accepted session to the engine of the identity it names
  └─ DocsApi, Doc (api.rs)  ── handles calling the engine; derefs from Docs
       └─ Engine (engine.rs)        ── coordinates everything below; holds Endpoint, blob store, default author
            ├─ SyncHandle (actor.rs)        ── store/replica operations
            └─ LiveActor (engine/live.rs)   ── live sync coordination
```

**The handles** (`api.rs`): `DocsApi` and `Doc` hold the engine weakly and call it directly; `Docs` holds the one strong reference. A `Doc` can sit inside what the engine holds — the data layer's access provider keeps a registry of every pod's `Doc` — so a handle holding the engine strongly would keep it alive for good. Once the last `Docs` is gone, a call on a handle fails with "the store has stopped" (`a_doc_the_access_provider_holds_stops_with_the_last_docs` in `tests/client.rs`). Calls from one task keep its order; calls from several tasks meet first at the sync actor. A call runs in its caller's future, so a dropped caller or another task's call can fall between its steps: `Doc::set_bytes` hands its payload's temp tag to the held payloads on every exit, and `DocsApi::drop_doc` is one message to the live actor, which leaves and deletes the replica, closing every handle of it first, another caller's open included (`a_drop_with_another_open_outstanding_deletes_the_replica`). `DocsApi::open` answers `None` for a namespace the store does not hold and an error for one it holds and cannot open. A write lands in batches the two stores commit on timers of their own — the replica store's within 500 ms of its last write (`MAX_COMMIT_DELAY`), the blob store's metadata, where a small payload lies inline, within a second — so an entry can reach the disk before its payload. A session's snapshot commits the replica store's batch without syncing the file, so it is readable at once, and the actor syncs it by the same deadline whether it is idle or not (`Store::sync_due_in`): a sync per session would queue every session behind the disk. `DocsApi::flush` commits both, payloads first, and answers that failure; a commit the actor's idle timer saw fail is kept and answered by the next `InsertLocal`, `Delete` or flush (`a_failed_idle_commit_fails_the_next_write`), and a failed sync is due again `MAX_COMMIT_DELAY` later, since redb refuses every commit after an I/O error and a sync due at once would keep the actor from every request (`a_store_whose_disk_stays_full_keeps_answering`); every public write method says so in its doc, and a caller flushes before anything durable outside the stores names what it wrote (the data layer's `durable-storage` spec).

**Data model & reconciliation core** (no I/O, no networking):
- `sync.rs` — the big one. `Replica`/`ReplicaInfo`, `SignedEntry`/`Entry`/`Record`/`RecordIdentifier`, `Capability`/`CapabilityKind`. `ProtocolMessage = ranger::Message<SignedEntry>` is what goes on the wire. `Capability` is an enum of the one variant `Write`, so a ticket's encoding carries its variant index, and the namespaces table stores the kind byte `1`: a ticket and a store file written before a change read the same after it (`test_ticket_base32` in `src/ticket.rs` and the test of `Capability::raw` beside it pin both).
- `ranger.rs` — generic range-based set reconciliation. Defines the `RangeEntry`/`RangeKey`/`RangeValue`/`Store` traits and the `Message` exchange. The doc types in `sync.rs` implement these traits.
- `keys.rs` — `Author`/`AuthorId`, `NamespaceSecret`/`NamespaceId`, wrapping `iroh::SecretKey`/`PublicKey`.
- `heads.rs` — `AuthorHeads` (latest timestamp per author), used in sync reports for cheap "are we in sync?" checks.

**Storage** (`store.rs` + `store/fs/`):
- `store::Store` (re-export of `store::fs::Store`) is the *only* store implementation, always backed by [`redb`]. "In-memory" = redb on a `Vec<u8>` backend; "persistent" = redb on a single file. It implements `ranger::Store`, so reconciliation runs directly against redb.
- `store/fs/tables.rs` — redb table layout (records, the `records_by_key` index, namespaces, authors, `latest_per_author`, `namespace_peers`). `Store::new_impl` creates every table on open and runs no migration: no node of ours holds a store an older format wrote.
- Every entry's content is wanted: a remote insert fetches it, or parks it when the sender lacks it.

**The sync actor** (`actor.rs`): `SyncHandle` is a cheaply-cloneable handle to a dedicated **`std::thread`** (`"sync-actor"`) that owns the `Store` and processes `Action` messages sequentially. It is a thread, not a tokio task, because **redb is blocking**. All replica mutation goes through here; the last handle drop joins the thread. On shutdown the actor closes and empties its channel: a request queued behind the shutdown would otherwise keep its reply open for as long as any handle lives, and its caller would wait forever. Prefer `SyncHandle::shutdown().await` over relying on drop to avoid blocking an async context.

**The live engine** (`engine/`): `Engine` ties the `SyncHandle`, a `LiveActor`, and a per-document gossip swarm together. `live.rs` is the coordinator — it serves sessions the protocol handler has already read, drives syncs, and reacts to gossip `Op`s: a `SyncReport` by pulling over reconciliation, a `ContentReady` by triggering a blob download. `state.rs` tracks per-namespace sync state (`Origin`, `SyncReason`); `gossip.rs` manages the swarm and drops a `Put`, since entries never ride the topic. Blob collection protects the payloads docs reference through `Engine::collection_hashes`, which the embedder's protect callback calls. An engine holds nothing of the node it runs in but the sending end of `CoLocatedRequests`, the channel it hands local-write announcements and dials to this node's own endpoint to: a callback into the node that owned something of it would close a cycle through the engine.

**Networking** (`net.rs` + `net/codec.rs`): ALPN is upstream's `/iroh-sync/1`. `connect_and_sync` is the initiator ("Alice"), `handle_session` the responder ("Bob"); `codec.rs` holds the wire state machines (`run_alice`, `BobState`) that exchange `ranger::Message`s over an iroh QUIC bi-stream. An accepted connection is read by the protocol handler — `accept_session`, then `handle_session` or `refuse_session` — never by the engine: an engine takes a session whose first message is already read, so no accept path waits on the wire inside the live actor's loop. That first message is read under `MAX_OPENING_FRAME`, before anything classifies the caller, and the session ceiling applies only once `SessionOpening::into_parts` hands the reader on; the opening's size is bounded by `MAX_KEY_BYTES`, which `validate_entry` enforces on every local write and at ingest.

## Conventions & gotchas

- `#![deny(missing_docs, rustdoc::broken_intra_doc_links)]` at the crate root: every public item needs a doc comment and intra-doc links must resolve. Some internal modules opt out with `#![allow(missing_docs)]`. `missing_debug_implementations` is also warned.
- `EntrySignature` wraps `iroh::Signature`, not the raw `ed25519_dalek` type, to keep the on-wire `SignedEntry` format independent of upstream ed25519 serde changes — don't "simplify" this.
- Every session is judged by the embedder (ADR-0014): the engine is assembled with a `SessionAccessProvider`, which answers for a dial and an accept alike either a refusal or an `EntryFilter` with a `SessionIngest` (`src/filter.rs`). `SessionStore` computes every fingerprint, split and item the session sends over the entries the filter admits, and `validate_entry` refuses an entry whose hash and length disagree on emptiness, then runs the ingest verdict on every entry the peer offers — `ValidateOutcome::Accept` stores it, `Drop` keeps it out in silence and the sender offers it again; nothing travels back about it. A refused session ends with the frame a namespace the engine does not host produces.
- An entry affects only its own key, per author: `ranger::Store::put` compares against the entry at that key alone, an empty one included, read through `entry_get`, and `Replica::delete` / `Doc::del` write an empty entry at one key. The rule is specified in the data layer's `reconciliation-sessions` spec.
- A read across authors orders entries as `put` does within one: `LatestPerKeySelector::push` picks the greater `(timestamp, content_hash)`, so equal timestamps resolve by content hash, as the data layer's `private-metadata-store` spec states.
- No actor waits on a subscriber outside the crate: `subscribers.rs` gives each subscription a `Delivery`, and every one opened through the public interface is `Lossy` — a full channel drops the event and a `Lagged` follows the last one received. Only the live actor subscribes to a replica `Blocking`, through the crate-only `OpenOpts::subscribe`. The sync actor then waits on the live actor, so the live actor waits on the sync actor only through `DrainingSync` (`src/engine/live/draining.rs`), which keeps taking its events meanwhile and keeps the raw handle for spawned tasks: a first catch-up inserts a whole store in one step, and a bare wait behind that step leaves both actors waiting for good once the 1,024 events of the channel fill it. A sync actor call the live actor makes goes through `DrainingSync`; `a_reply_arrives_while_the_sync_actor_waits_for_room_for_its_events` there and `a_catch_up_past_the_events_channel_finishes_while_the_live_actor_asks_the_sync_actor` in `tests/sync.rs` pin it. A subscriber that stopped reading would otherwise stop the actor and every replica it serves. The contract is specified in the data layer's `change-subscription` spec.
- Behind the `observation` feature, which `data-layer/test-util` turns on and no product build carries, the live actor keeps ordered subscribers beside the product's: `Engine::observe` registers one for a replica already syncing, and `Engine::sync_with_peers_observed` registers it before the replica is opened for sync, so it sees that sync from its first event. The actor hands an ordered subscriber each insert as it handles the replica's event, ahead of the download the insert queues, and then the content and session events in the order it emits them (the data layer's `change-subscription` spec). A product build compiles out the `Observe` message and that dispatch, never derives the session id, and keeps everything else of the live actor as it is: the product's subscribers, the events and `SyncEvent` itself.
- `SyncEvent::session` names a session over a network connection by 16 bytes both ends export from the connection's keying material (`session_id` in `src/net.rs`), so the two ends' events of one session pair; nothing new crosses the wire, and an in-process session or a dial that never connected carries none. It is exported under the `observation` feature alone; a product build reports `None`.
- A sync can be handed the peers it dials: `Doc::sync_with_peers` hands `Engine::sync_with_peers` the recorded peers to dial, and the live actor then dials those recorded peers and the contacts alone, where `start_sync` unions in every peer the store recorded. The data layer starts a pod's stores and runs its pass over them this way, with no recorded peer, the pass drawing a few contacts per run, as its `pod-store` spec states. `Doc::share` restarts the sync as `start_sync` does, every recorded peer included; `Doc::ticket` mints the same ticket and leaves the sync as it is, and the data layer mints a pod store's tickets with it, so a join a member's device serves dials no former member's device.
- A namespace can be ordered after another: `Engine::order_after` makes every later dial of it follow an exchange of the other with the same counterpart — the one the dial then starts, or the one running — holding the dial until that exchange ends, in-process dials included, whose consumer opens the first exchange itself. A pod's record store follows its membership store this way, and a dial of the first refused as already syncing keeps the held ones held until its redial or the incoming exchange ends, so the record store is judged on the membership the exchange brings. An exchange a resync was queued behind leaves them to the resync, which dials the pair that queued it, and an in-process dial the co-located channel dropped releases them itself. `a_dial_refused_as_already_syncing_leaves_the_ordered_dial_held` and `a_dial_held_behind_an_exchange_with_a_resync_queued_follows_the_resync` in `tests/sync.rs`, `a_dial_held_behind_exhausted_redials_starts_once_they_are` in `tests/dispatch.rs` and `a_dial_held_behind_a_dropped_in_process_resync_starts` in `tests/observe.rs` pin the four.
- A finished session's `SyncEvent` names its `counterpart`, the identity the peer's side was — the one a dial named, the one an accept's caller acted for — since one node id hosts several identities (ADR-0013), and its details carry `snapshot_writes`, the replica's write count (`SyncHandle::writes`) as the session's snapshot opened, so a session that served a write tells itself apart from one set up before it, however late that one ends: the data layer counts a pod tombstone's convergence by both.
- `Engine::state_contacts` replaces whom each peer of a namespace is dialed as, without dialing: identities learned in a session last only as long as it, so a consumer whose peers' identities change with its own records — a pod's members — states them again on every change.
- A peer no contact or running session names is dialed as the replica's default identity, which every `start_sync` states and `Doc::share` keeps — a share sets this engine's own identity only for a replica no start stated one for, and `Doc::ticket` touches neither. A pod store imported from another member's ticket keeps that member as its default: restated as the holder, the dials a neighbor's arrival makes would address the inviter's device, while derived contacts still leave it out, as an identity that device does not host.
- A session's report of news names the heads of the entries the store took, never one it refused, since its sender offers it again in every session (iroh-docs-004), and of those the newest that fit gossip's limit on a message's content with the report around them (`sync_report_message` in `src/engine/live.rs`); gossip's refusal of a message over its limit is a warning: sized by the whole message's limit, as upstream sizes it, a session that brought 100 authors or more sends no report at all (iroh-docs-003).
- A pull of reported news addresses the identity the report names when no contact or running session names its sender and the consumer named that identity for the replica — as a contact's or as the replica's default — and otherwise as `identities_of_peer` does: `SyncReport` carries the identity the sender's replica answers as, and that name is the sender's word, so a sender naming fresh identities would otherwise open a slot and a dial for each. The access provider judges the session on both sides.
- A dial the remote aborts as already syncing is asked for again half a second later, whatever finished meanwhile: the remote's own exchange may be one this side's access provider refuses — a replica holding nothing yet judges no caller — and then neither exchange runs, or one whose view of the remote froze before the news this dial was for. A pair is redialed at most 3 times in a row, each wait twice the one before, the count cleared by an exchange that finishes: the remote picks the abort's reason, and one answering every dial so would otherwise keep a redial going forever (`a_remote_always_syncing_is_redialed_a_bounded_number_of_times` in `tests/dispatch.rs`).
- A pair that refused this side's last dial with the uniform refusal takes the pair over with a dial of its own crossing one of ours, whatever the tie-break; a session with the pair that goes through ends that standing (`refused_dials` in `src/engine/live.rs`, `refused_ours` in `src/engine/state.rs`). Otherwise a side the other refuses keeps a dial in flight under a short pass and the tie-break aborts every dial of the side it would serve: a device that joined a pod refuses its inviter until its membership view counts a member, and on half a CPU its join did not catch up within its 30 s in about one run in four of `a_member_whose_removal_stops_counting_holds_the_pod_again` in pdn-node's `tests/pods.rs`. `a_dial_crossing_one_its_pair_refused_takes_the_pair_over` in `src/engine/state.rs` pins it.
- A sync dial that fails to connect, and a payload download that fails to connect, loses its connection or makes no progress, toward a gossip neighbor are tried again — 1 s later, each wait doubling to 16 s, for 2 minutes after the first failure — until an exchange with the pair ends any way but a failed connection, a download from the peer succeeds or the peer stops being a neighbor in every swarm (`retry_unreached_dial` in `src/engine/live.rs` for a dial, the provider's series of pauses in `src/engine/live/fetches.rs` for a download). A series arms one timer at a time and stays run out until what ends it, so a failure another trigger brings neither adds a timer nor starts the series again; a try due after the replica is left does nothing. The neighbor set follows live subscriptions only: a gossip event names its subscription's generation, and one sent before a quit is dropped. A node's endpoint installs the data layer's `ReceivingPathSelector` in place of iroh's own (iroh-001); the store's own test endpoints keep iroh's. `a_dial_toward_a_neighbor_it_cannot_reach_is_tried_again`, `a_dial_toward_a_peer_that_is_no_neighbor_is_not_tried_again`, `a_series_toward_a_neighbor_keeps_one_try_armed` and `a_download_from_a_neighbor_is_tried_again_until_the_replica_is_left` in `tests/dispatch.rs` pin it.
- An engine fetches each payload from one provider it chooses, through a connection pool and iroh-blobs' `execute_get` over a stream it opens itself — iroh-blobs reports a stream that fails to open as a local failure (iroh-blobs-007) — in a task the live actor owns, so dropping the task frees the request's stream; iroh-blobs' `Downloader` holds a request a silent provider never answers for good (iroh-blobs-006). At most the builder's `fetches_per_provider` fetches are in flight toward one provider — the data layer sets it to the bidirectional streams its endpoint grants a connection — and every other wanted payload waits in the queue of each provider registered for it, a pair of payload and provider queued once (`Fetches` in `src/engine/live/fetches.rs`). A fetch with no progress for 10 s is dropped and its payload goes back to the queue of every provider registered for it; the provider pauses 1 s, doubling to 16 s, for 2 minutes, one fetch probing it after each pause and a success ending the pauses, and a fetch failing on the node's own blob store pauses no provider and parks its payload; a fetch iroh-blobs reports done has landed only once the blob store holds the payload whole (`landed` in `src/engine/live.rs`, iroh-blobs-008). The pool bounds attempts to connect only as it bounds connections (`fetch_pool_options`): an attempt it turns away fails as a connect does, which drops a provider that is no gossip neighbor. A provider's answer that it lacks the payload, whole or in part, drops that pair alone and pauses nothing (`outcome_of_failure` in `src/engine/live.rs`): a session's end registers its peer for payloads it may not hold. A finished session registers its peer for the namespace's waiting payloads with no blob store call in the loop; the fetch reads the store once and asks the provider for what it lacks, and a payload it finds whole is reported as an insert finding it whole is, with no `ContentReady`. Specified in the data layer's `reconciliation-sessions` spec; `a_catch_up_keeps_the_limit_toward_its_provider`, `a_provider_registered_during_a_catch_up_takes_waiting_payloads`, `a_silent_providers_payloads_come_from_another_provider`, `the_only_provider_silent_for_a_while_is_asked_again` and `a_neighbor_lacking_a_payload_has_its_own_fetched_at_once` in `tests/sync.rs`, `a_payload_the_blob_store_fails_to_write_is_a_local_failure` and `the_fetch_pool_turns_away_no_attempt_to_connect` in `src/engine/live.rs` and the unit tests of `fetches.rs` pin it.
- A dial the consumer asks for, or a neighbor's arrival prompts, while an exchange with the same counterpart runs is run again once that exchange ends, as one news prompts is, whichever exchange holds the slot by then: the running exchange began before the ask and may carry nothing written since, and the replay outlives a takeover of the slot by the remote's exchange in the tie-break: under `order_after` a record store's dial held behind its membership store's exchange is released just as the counterpart's own released dial runs, and a dropped dial would leave a write behind until the next pass. A neighbor's arrival is replayed at the cost of a session added to nearly every join: dropped, a write that reached this side during the exchange, after its post-sync report went to the neighbors it had then, never reaches the newcomer while the swarm stays quiet. `a_dial_asked_for_during_a_running_exchange_is_run_after_it` and `a_takeover_keeps_the_resync_queued_on_the_dial_it_supersedes` in `src/engine/state.rs` pin it.
- A completed exchange stands whatever its teardown meets: the counterpart can drop the connection before this side's `stopped()` or `read_to_end` hears from it, and everything it sent has arrived, so the teardown error is logged and the exchange reported as it went: reported failed, it would be passed by by the post-sync report, the retry of parked content and every wait for a successful session — a join's catch-up among them.
- A pair's one slot is finished only by the exchange that holds it: an accept this side refuses never takes the slot, so its end leaves alone the dial of ours that holds it, and that dial's end is the one reported. The access provider's uniform refusal hits a namespace that syncs, and a refused accept finishing the slot would swallow the dial's `SyncFinished` — a pod's join waiting for its catch-up would never hear of the session it waited for.
- Content an entry lacks is parked in memory, and a `start_sync` of a namespace the live actor is not syncing — its first, or its first after a leave — parks the content of every entry the blob store does not hold whole: a session after a restart exchanges no record, so content whose download the restart cut short is asked for again by nothing else. The scan reads every entry of the replica and asks the blob store about each, once per such start, in a task off the actor's loop, so neither `start_sync` nor any other message waits on it; the actor parks what the scan found when it reports back (`ToLiveActor::ContentScanned`), and asks for it at once from the peer of a session that went through while the scan ran, since that session's retry of parked content came first. `content_a_restart_left_missing_is_fetched_from_the_first_sync_peer` in `tests/sync.rs` proves it.
- A dial asks the access provider once the connection stands and the session's egress snapshot is open, inside `run_alice` (`DialAccess::Asked`), never when the dial is asked for: a connect waits for as long as the peer is down, and a decision taken before it, applied to a snapshot taken after, serves entries written after the access changed — a removed member's device once received a record placed after its removal that way. `a_dial_decided_before_a_removal_takes_nothing_placed_after_it` in the data layer's `tests/pod_tombstone.rs` pins it. `connect_and_sync` keeps a filter its caller decided, for the callers that serve by their own word.
- An accept asks the access provider before it opens the snapshot, so a caller it refuses takes no slot of the engine and forces no commit of the pending write batch, and the decision says what it read: `SessionAccess::Allow`'s `rests_on` names replicas at their write counts, the step that opens the snapshot compares them (`sync_session_start_unless_written`), and a decision whose replicas were written in between, or one resting on something no count shows (`RestsOn::Unknown`), is asked again through `Recheck::ask` before the first message is served, its answer standing. A refusal on that second ask goes out as the uniform refusal and ends the session as a failed exchange: the pair's slot is the session's by then, and a refusal reported as one before the slot would leave the pair's slot taken until a restart (`a_session_refused_when_asked_again_frees_the_pairs_slot` in `tests/dispatch.rs`). `an_accept_decided_before_a_removal_takes_nothing_placed_after_it` in the data layer's `tests/pod_tombstone.rs` and `an_accept_decision_is_asked_again_when_what_it_read_was_written` in `net/codec.rs` pin it.
- A payload a replica of the engine comes to reference — a local `Doc::set_bytes`, or a remote insert — is held by a temp tag until the next `Engine::collection_hashes`, which takes the held tags before it reads the replicas and drops them after. A collection run whose read predates the entry would otherwise remove the payload between its read and its sweep, and a local write's payload has no other copy. The engine holds nothing until a collection first reads through that call, so a store no collection runs over keeps no tags. `a_payload_written_while_a_run_is_under_way_stays` and `a_payload_fetched_while_a_run_is_under_way_stays` in the data layer's `tests/blob_collection.rs` pin it.
- The live actor's wait for a gossip receive loop to end stays pending while no loop runs (`GossipState::next_ended` in `src/engine/gossip.rs`): a runtime shutting down cancels the loops while their topics stay joined, and an answer of "none left" there is ready on every turn of the actor's `select!`, which then spins inside one poll and holds the runtime's shutdown forever.
- `Engine::syncs_in_flight` counts a set of namespaces' exchanges running, held behind another's and due to redial, so a scenario can wait until nothing this engine started can still dial: out of a swarm a replica is still dialed by every node it had a session with; `syncs_in_flight_report` names each, for a failure message.
- Property tests use `proptest` + `test-strategy`; regression seeds are checked in under `proptest-regressions/`.
