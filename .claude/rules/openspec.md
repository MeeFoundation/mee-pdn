# OpenSpec (mia-docs)

## Integration files

- **The generated skills and commands are stock openspec output; project specifics live in `mia-docs/openspec/config.yaml`.** `context` and `rules` reach every artifact instruction; `operations.apply.guidance` and `operations.archive.guidance` come back from `openspec instructions apply|archive`, which the apply and archive skills read at run time. An edit to a generated skill is lost on the next `openspec update`.
- **Two copies, one source.** `mia-docs/` is the openspec root: `openspec update` (profile `core`: propose, explore, apply, update, sync, archive) writes `.claude/` (skills and the `/opsx:*` commands), `.agents/skills/` (Codex as `$openspec-*`, other agents as `/openspec-*`; `.openspec-target` there is openspec's ownership marker, kept committed) and `.opencode/`. The workspace root is not an openspec root, so its `.claude/skills/openspec-*` and `.agents/skills/openspec-*` are derived from mia-docs by `just openspec-skills`, which prefixes every `openspec` command with `cd mia-docs &&` and touches nothing else. To follow an openspec release: `cd mia-docs && openspec update`, then `just openspec-skills`, then review the diff. From the workspace root invoke the skills (`/openspec-propose`); inside `mia-docs/`, the `/opsx:*` commands.

## Spec tree

- **`openspec validate --all --strict` before archiving a change.** It is a parser gate for change deltas and main specs, not a review: it checks that delta files parse (`## ADDED/MODIFIED/REMOVED/RENAMED Requirements` sections), that a MODIFIED requirement exists in the main spec and drops none of its scenarios, and that every requirement keeps at least one `#### Scenario:` block. It does not check content — SHALL wording, WHEN/THEN completeness, or truthfulness.
- **Scenario headers must be exactly `#### Scenario:` (four hashes).** A wrong heading level drops the scenario from parsing _silently_ — validation still passes if the requirement retains another scenario. Heading levels are checked by eye, not by the tool.
- **A capability spec is `specs/<path>/spec.md`, and the tool sees it.** `openspec validate --specs --strict` parses every one and `openspec archive` lands a delta at its path. What the tool still does not do stays by hand:
  - **Sweep the whole tree when a change removes or renames things.** A change's own deltas are not enough — grep `openspec/specs/**` for names of removed types/tests/mechanisms (precedent: multi-identity-node removed `Binding`/`BindingIndex`, and `mee-pdn/pdn-node/namespace-addressing/spec.md` kept naming them until noticed by accident).
  - **Sweep other active changes too.** A change landing first can invalidate assumptions in a sibling change's proposal/design (precedent: subset-rbsr referenced the removed ingest gate, a deleted test, and one-identity phrasing in D4 long after multi-identity-node landed).
  - **Keep `architecture/language/` in sync.** A term used by specs (e.g. swarm) gets a glossary entry there, and the spec links the term's first use to it.
  - **Verify spec scenarios against running code before writing them down.** A plausible formulation once claimed a zero-length write degenerates into deletion; the engine actually rejects it (`AttemptedToInsertEmptyEntry`). Each scenario should correspond to a test or a checked property of the fork.
  - **A capability the change creates gets the tree's title and a real `## Purpose` after archive.** The CLI writes `# <capability id> Specification` and a TBD Purpose when the delta carries none; the tree's titles are words (`# Reconcile trigger`).
- **`components/` holds product components; the workspace's crates sit under `components/mee-pdn/<crate>/<topic>/spec.md`.** One directory per crate, named as the crate is (`data-layer`, `pdn-node`, `pdn-node-http`, `pdn-layer`, `pdn-store`). The capability id is the path (`components/mee-pdn/pdn-node-http/host`), a delta sits at `changes/<name>/specs/<that path>/spec.md`, and links inside a delta are written for its place in the main tree, not for the change directory — a delta that links a sibling delta's capability resolves once both land. Documents without requirements keep `<name>.md` at the same places (`components/mee-pdn/invariants.md`, `components/mee-pdn/pdn-layer/uwill.md`) and the tool ignores them. A spec whose mechanism spans crates lives with the crate whose scenario tests prove it (`capability-gated-ingest` with `data-layer`, `uwill` with `pdn-layer`). The other components keep `components/<component>/<topic>/spec.md`.
- **An ADR with `status: obsolete` is a stub on purpose.** Its text was erased when the decision stopped describing anything, and git history holds it (`git log --follow -p -- <path>`); the conventions are in `openspec/specs/architecture/adr/meta/rationale.md`. Do not refill it, do not cite it as a current decision, and do not reuse its number. Making one obsolete includes the sweep above: every `ADR-NNNN` citation in the spec tree either goes away or moves to the decision that replaced it.
